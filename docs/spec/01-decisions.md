# 01. 착수 결정 사항

각 결정은 "결정 / 이유 / 대안 / 재검토 조건"으로 기록한다.

## D1. 연동 증권사: 한국투자증권 KIS Developers Open API

**결정**: 한국투자증권 KIS Open API를 Phase 2 연동 대상으로 한다.

**이유**
- REST + WebSocket 방식이라 OS 제약이 없다. Linux 서버, macOS, Python 64bit에서 그대로 동작한다.
- 모의투자 계좌를 API로 지원하고, 모의투자 전용 TR이 실전과 짝을 이룬다. 대사에 필요한 두 가지가 모의에서 모두 된다.
  - 실시간 체결통보: 실전 `H0STCNI0`, 모의 `H0STCNI9` (WebSocket)
  - 주식 잔고조회: 실전 `TTTC8434R`, 모의 `VTTC8434R` (REST, 모의는 1회 20건씩 연속조회)
- 증권사가 직접 운영하는 공식 GitHub(koreainvestment/open-trading-api)에 Python 샘플이 있고, 개인 개발자 커뮤니티 자료가 가장 많다.

**비교한 대안**
| 증권사 | 판단 |
|---|---|
| 키움 REST API (2025년 출시) | REST+WS, 모의 도메인 지원. 유력한 2순위. 공개 호출 한도 수치와 공식 Python 샘플이 상대적으로 적다. |
| LS증권 Open API | REST+WS, 체결통보(SC0/SC1) 명확. 신청 시 공동인증서와 xingAPI 등록이 먼저 필요하다. |
| 토스증권 Open API | REST+WS, 한도 정책이 가장 투명하다. 다만 공식 명세에 모의투자 환경이 없어 "모의 4주 대사" 게이트를 만족할 수 없다. |

**재검토 조건**: 모의투자에서 체결통보나 잔고조회가 실측상 불안정하면 키움 REST API로 전환한다. 이를 위해 증권사 연동은 어댑터 인터페이스(`BrokerGateway`) 뒤에 둔다.

**보안**: 앱키·앱시크릿·계좌번호는 리필의 로컬 환경 변수로만 둔다. Claude 작업 환경과 저장소에는 넣지 않는다.

## D2. 매입 단가: 이동평균법 (총액 기준 관리)

**결정**: 이동평균법을 주 방식으로 한다. 단, 단가를 저장하지 않고 **종목별 취득원가 총액(book_cost, 원 단위 정수)과 수량**을 저장한다. 단가는 표시용으로 `book_cost / qty`로 계산한다.

**이유**
- 증권사가 보여주는 평균단가가 이동평균이라 대사가 가능하다.
- 총평균법(기간 가중평균)은 기간이 끝나야 단가가 정해져 매도 시점 실현손익과 일별 기준가를 낼 수 없다.
- 총액으로 관리하면 단가 반올림 오차가 누적되지 않고, 전량 매도 시 원가가 정확히 0이 된다.

**확장**: 원장은 append-only 이벤트이므로 선입선출·총평균 결과를 재계산 리포트로 낼 수 있다(확장 1).

## D3. 기술 스택: Python 모듈러 모놀리스 + PostgreSQL

**결정**
- 언어: Python 3.12, 금액은 `decimal.Decimal` 또는 정수 원 단위만 사용 (float 금지)
- DB: PostgreSQL 16. 원장 테이블은 append-only를 DB 수준에서 강제한다 (UPDATE/DELETE 금지 트리거, 분개 차대변 일치 검증)
- 구조: 하나의 Python 애플리케이션 안에서 모듈 경계를 나눈다 (`marketdata`, `strategy`, `backtest`, `oms`, `broker`, `ledger`, `accounting`, `recon`, `reporting`). 모듈 간에는 이벤트와 인터페이스로만 통신한다.
- 테스트: pytest. 04-sample-trades.md의 기대값이 그대로 게이트 테스트가 된다.

**이유**: 금융권 표준의 핵심은 "트랜잭션과 제약조건이 있는 DB에 원장을 둔다"이다. 서비스 분리는 주 5시간 개발에서 운영 부담만 키운다. 아키텍처 문서에 "ledger 모듈은 그대로 별도 서비스로 분리 가능"을 보여준다.

**재검토 조건**: 다자산 확장(Phase 5)에서 24시간 시장 처리가 필요해지면 ledger 분리를 검토한다.

## D5. 저장소 공개 범위

**결정**: 저장소는 공개한다. 공개 대상은 스펙, 원장·OMS·대사 코드, 예시 전략(이동평균 교차 1개), 대사 리포트 샘플(가상 데이터), 아키텍처 문서, 데모 영상이다. 개인 전략은 `strategies/private/`에 두고 `.gitignore`로 제외한다. 계좌번호, 키, 실제 잔고 수치는 어떤 형태로도 커밋하지 않는다.

**이유**: 채용 담당자에게 보여줄 것은 수익 전략이 아니라 원장 정합성과 통제 설계다.

## D6. IBOR와 ABOR: 원장 하나, 보기 둘 (초안, 리필 확인 필요)

**결정**: 장부를 두 벌 만들지 않는다. 같은 append-only 이벤트 원장에서 두 가지 보기를 만든다.

| | IBOR (투자 장부) | ABOR (회계 장부) |
|---|---|---|
| 목적 | 장중 의사결정: 지금 얼마나 보유하고 얼마를 더 살 수 있나 | 확정 기록: 일별 기준가, 손익, 분개 |
| 반영 시점 | 체결 즉시 (매매일 기준) | 일 마감 이벤트(`DayClosed`) 이전 이벤트만 |
| 포함 범위 | 체결 + 미체결 주문 예약분 + 실시간 시세 평가 | 체결, 결제, 종가 평가, NAV |
| 대사 | 장중 수시 (보유수량, 결제 후 예상 예수금) | 장 마감 후 전 항목 (R-70~75) |

- 체결은 실시간 체결통보(WebSocket H0STCNI9/H0STCNI0)로 받아 통보에 담긴 체결별 수량·가격으로 즉시 원장에 넣고, 증권사 누적 조회(`daily_orders`)로 확인한다(v1.27). 통보가 끊기거나 빠지면 주기적 조회가 같은 경로로 빈 곳을 메운다(멱등, 누적 증가분만 반영).
- 주문가능금액 = IBOR 결제 후 예상 예수금 − 미체결 매수 주문 예약분. 사전 리스크 점검은 이 값을 쓴다.
- 일 마감은 `DayClosed(date)` 이벤트로 남긴다. 이 이벤트 이후에 들어온 그날 이벤트(늦은 체결 등)는 다음 장부일로 넘기지 않고 정정 이벤트로 처리한다.
- 장중 대사에서 불일치가 나면 그 시점에 원인 후보를 붙여 기록한다. 장 마감 대사는 그날의 확정 판정이다.

**구현 상태 (v1.5)**: 체결통보 즉시 반영, 조회 보완, 주문가능금액, 장중 대사(`INTRADAY_RECON`, 게이트 집계에서 제외), 단일 기록자 잠금, 체결 반영 지연 기록(`FILL_NOTICE`), 현재가 평가(R-68, v1.22)까지 구현. `DayClosed` 마감 이벤트와 ABOR 보기는 Phase 3.

**이유**: 실제 운용사와 증권사는 장중 포지션(IBOR)과 회계 확정 장부(ABOR)를 따로 두는 경우가 많고, 둘 사이의 차이를 맞추는 일이 사무관리의 큰 비용이다. 이벤트 원장 하나에서 두 보기를 만들면 두 장부가 구조적으로 어긋날 수 없고, 차이는 "아직 마감되지 않은 이벤트"로만 설명된다.

## D7. 계좌 모델: 리테일 위탁 고객계좌 (확정, 2026-11-22 리필)

**결정**: 다계좌(Phase 3)의 "계좌"는 증권사 리테일 계정계의 **위탁 고객계좌**로 본다. 프랍(자기매매)의 데스크·북이나 운용사의 펀드 여러 개로 보지 않는다.

| | 리테일 위탁 (선택) | 프랍 (자기매매) | 펀드 (운용사·사무관리) |
|---|---|---|---|
| 관리 단위 | 고객 계좌 | 데스크·북·트레이더 | 펀드 |
| 핵심 숫자 | 예수금, 주문가능금액, 결제 | 실시간 손익, 한도 소진율, VaR | 기준가, 좌수, 수익률 |
| 주문 경로 | 고객 → 증권사 → 거래소 | 증권사가 회원사로 거래소에 직접 | 운용사 → 브로커 증권사 |
| 회계 | 고객 자산(회사 B/S 밖) | 회사 B/S의 단기매매증권 | 펀드 별도 장부 |

- 지금 구조는 펀드 원장(1,000좌당 기준가, 좌수, 출자금)에 위탁계좌 개념(예수금 D+n, 주문가능금액, 매도가능수량, 체결통보, 증권사 대사)이 붙은 형태다. 다계좌에서 원장은 계좌별로 나뉘고, 기준가는 **계좌별 성과(수익률) 보기**로 남긴다.
- 계좌 테이블에는 별칭, 증권사, 계좌 유형, 상태, 표시용 값만 둔다. 계좌번호 원본과 인증키는 계속 DB 밖(사용자 PC 환경)에 둔다.
- 컴플라이언스는 고객 주문 제한(주문가능금액, 증거금, 매매 금지 종목, 일일 매매 한도) 중심으로 설계한다.
- 프랍은 거래소 회원사 지위가 전제라 개인 시스템으로 재현하지 않는다. 필요하면 데스크 한도·실시간 손익 화면 정도만 보조로 붙인다.

**세부 결정 (2026-11-22 리필)**

1. 고객 테이블을 둔다(고객 1 : 계좌 N). 실명 등 개인정보는 저장하지 않고 별칭만 둔다.
2. 계좌 유형은 위탁종합(GENERAL)만. ISA·연금저축은 세금 계산이 달라 별도 설계.
3. 출금·계좌 간 대체 이벤트는 ERD v2.0 다음 PR로 분리한다(테이블 변경 없이 이벤트 유형만 추가).
4. 두 번째 계좌는 샘플 DB의 가상 계좌로 먼저 시험한다.
5. 수수료는 v2.0에서 공통 한 벌. 계좌별 수수료 등급은 기준정보 변경 화면(적용시작일 이력)과 함께.
6. 원장은 나누지 않는다. 이벤트 원장 하나에 계좌ID를 붙이고 순번은 전체에서 하나로 유지한다. 기존 데이터는 계좌 `A0001`의 기록으로 남긴다(03 스키마 변경 규칙).

**이유**: 목표 직무가 증권사 IT 기획/PM(계정계)이고, 이미 만든 기능(주문가능, D+n 예수금, 체결통보, 대사)이 모두 위탁 계정계 용어다. 계좌의 뜻을 스키마 변경 전에 정해 두면 Phase 3 테이블이 한 번에 정해진다.

## D8. 리스크·컴플라이언스·PMS: 별도 시스템이 아니라 같은 원장의 보기와 규칙 (구상, 미착수)

**구상**: 실무에서는 OMS, PMS, 리스크, 백오피스가 따로 있어 서로의 포지션을 다시 맞추는 대사가 생긴다. MiniSTP는 이 셋을 별도 시스템으로 만들지 않고, 같은 이벤트 원장 위의 규칙과 보기로 붙인다. 그래서 세 기능이 보는 숫자가 원장과 어긋날 수 없다.

| 순서 | 기능 | 범위 | 무게 |
|---|---|---|---|
| 1 | 컴플라이언스 | 사전 규칙을 데이터로(적용시작일 이력, R-11과 같은 방식): 동일종목 비중 한도, 매매 금지 종목, 일일 매매 한도. 장 마감 후 사후 점검, 위반은 대사 불일치처럼 기록하고 사람의 판단을 남긴다(R-74 구조 재사용). | 가벼움, 본기능 |
| 2 | PMS 지표 | 종목·자산별 비중, 목표 비중 대비 차이, 기간 수익률(TWR), 종목별 기여도, 벤치마크(KOSPI200) 대비 | 중간, 보조지표 |
| 3 | 리스크 지표 | 집중도, 일별 손익 변동, 최대 낙폭, 손실 한도 소진율, 과거 가격 기반 VaR(종가 이력 수집 필요) | 보조지표 |

- 시점: Phase 3 다계좌·감사 로그 다음. 규칙이 계좌별로 걸리기 때문이다.
- 하지 않는 것: 모델 포트폴리오에서 주문을 자동 생성하는 PMS, 별도 리스크 엔진.
